# 可选的结构模型与验证参考

自由画板是当前默认入口。此文保留器官、数据流、场景、架构规则和数值验证的兼容模型；仅在工程已采用这些数据或确有建模需要时使用。旧有平面/立体视图描述不代表当前界面，当前操作见主 README。

## 从工程文件到共同理解

锚点可以同时出现在器官、部件 `composition[].anchor` 和血脉上。一个文件可以承载多个职责，一个职责也可以跨多个文件；反查保留全部关系。给锚点补上用途与依据：

```json
{ "file": "src/order.ts", "symbol": "submitOrder", "role": "implementation",
  "reason": "接收订单并协调库存预留" }
```

`role` 支持 `implementation` / `interface` / `test` / `config` / `docs`，旧锚点未声明时按实现处理。测试文件用 `test`，并写明它验证什么；关联到测试文件不等于测试已执行或业务已覆盖。

```js
anatomy_mapping({ dir, scope: ["src", "test"] })
anatomy_mapping({ dir, files: ["src/order.ts"] })
anatomy_impact({ dir, files: ["src/order.ts"], depth: 2 })
```

`mapping` 列出未映射职责、缺少测试证据、缺少映射依据和未锚定的血脉。传 `scope` 才扫描指定范围内支持的源码与配置文件，排除隐藏目录、常见依赖和生成目录、符号链接，并设扫描上限。结果明确列出遗漏、跳过项、错误与截断；覆盖率只表示扫描到的文件被锚点引用的比例，不代表功能或测试覆盖率。扫描失败或截断时不给出完整覆盖率。

`impact` 沿已声明流向、双向连接、构成关系和共享实现/接口/配置文件传播；每个候选附到达路径、边界、相关场景和验证线索。默认追踪 2 跳，最多 5 跳。共享测试文件不会被当作实现依赖。它是待复核范围，不能替代真实调用图；还需查看 `check` 与 `sourceEvidence` 确认证据是否过期。

场景保存在同一份 `body.scenarios` 中，可随 `scaffold` 一次提交，或单独更新：

```js
anatomy_scenario_put({ dir, scenario: {
  id: "submit-order", name: "提交订单", trigger: "顾客确认购买",
  steps: [
    { organ: "order-entry", action: "接收购买意图" },
    { organ: "stock-reserve", flow: "reserve-request", action: "预留库存" }
  ],
  outcome: "订单获得库存预留结果",
  acceptance: ["库存不足时明确返回失败"]
} })
```

示例中的器官与血脉须先存在。第一步不带 `flow`，后续每步必须通过已有血脉连接前一步，方向也必须相符；悬空引用和断开的步骤会被拒绝。删除器官或血脉前需先更新引用它的场景，级联删除不会偷偷删掉业务意图。`MAP.md`、完整 `DIGEST.md` 与 HTML 都读取这份场景。

本仓库附有真实源码示例：运行 `node examples/coread-demo.mjs anatomy-my-demo`，会在新目录生成 anatomy 自身的映射、两条阅读场景、地图、摘要和交互图。它不会覆盖已有目录。

## 耗时、数学意图与实现验证

血脉可声明 `timing: { latencyMs: 8, basis: "estimated", method: "设计阶段估计" }`。测量使用 `basis: "measured"` 并说明测量方法；双向流另给 `reverseLatencyMs`。界面中的人读说明会明确“估计”或“测量”，未知值不会参与时间距离计算。

器官和血脉支持 `math`（自然语言与数学关系）、`acceptance`（自然语言验收）、`implementation`（机读实现说明）以及 `rules`（可核验数值规则）：

```json
{ "id": "response-time", "statement": "查询应及时返回", "metric": "响应耗时",
  "relation": "≤", "limit": 20, "unit": "毫秒" }
```

规则标识稳定绑定其器官或血脉。人在图上修改意图、数学关系或阈值，会连同规则标识进入版本化修改包；数值阈值以数值保存，不转成模糊文字。AI 读取 `brief` 或完整摘要后，必须核对受影响实现并运行关联测试。

1. 调用 `anatomy_verify({ dir })` 获取当前 `modelHash`、`sourceHash` 和待验证规则。
2. 在该版本运行测试，产生 JSON 报告，包含两个版本值、`method`、`observedAt` 和 `measurements`。每项测量包含 `rule`（例如 `organ:search:response-time`）、`value` 和 `unit`。
3. 调用 `anatomy_verify({ dir, file: "测试报告路径" })`。规则须同时关联实现锚点与测试锚点；单位不符、重复测量、无证据和版本过期都不通过。数值不满足返回失败。
4. 以 `anatomy_render({ dir, requireVerified: true })` 交付已实现结果；验证未通过时拒绝，`force` 无效。普通渲染允许讨论待实现的上层意图，但页面与回执会明确实现验证状态。

报告保存为 `verification.json`。意图或关联源码变化会使旧报告失效，即使普通源码基线已经复核，也需要重新执行验证。检查只核验所提供报告的版本、数值和文件绑定，不自动执行命令，也不证明报告本身诚实。任意自然语言意图及自由数学公式仍需要 AI 转成具体约束和测试；未形式化部分不得宣称已由工具证明。

## 强校验：四层门禁

一句话：**写的时候拦、交付的时候拦、规则可执行、结论可对账。**

### 1. 共读质量即门禁（strict，默认开）

体检分两档，`strict` 决定第二档算不算 error：

- **人读语言错误**（永远拦，force 也不绕过）：人读字段混入可识别的程序定义、调用、命令或源码路径。检查是语法线索检测，不是通用语言理解证明；作者仍需复核全部人读表达。
- **结构错误**（永远拦）：悬空引用、id 非法、重复、构成成环、缺一句话、自环、未声明物质…
- **工程与共读完整性**（strict 下升级为 error）：缺叙述、缺边界、缺有效成分、缺契约、缺锚点、锚点漂移、源码基线变化。成分至少有一条名字和作用；契约至少有一条输入、输出或不变量。
- **展示建议**（只提醒）：一句话偏长、系统同层。工程本身可以有同层系统，不需要为了图形排布改架构。
- 刻意**不**升级的：孤立器官、系统孤立——图还没长全是正常节奏，硬拦会让人没法一步步来。

放宽方式：插件配置 `strict: false`，或单次调用传 `strict: false`。

### 2. 架构规则可执行（anatomy-policy.json）

规则不是文档，是每次体检都会跑的门禁。五类规则（`anatomy_policy` 工具读写）：

| 规则 | 作用 |
|---|---|
| `forbid-flow` | 禁止某两个系统之间的血流 |
| `layer-direction` | 血流只能沿抽象层级向上或向下（用 `system.alt`）；跨层双向连接会违反任一单向规则，同层允许 |
| `max-organs` | 限制单个系统的器官数，防止上帝系统 |
| `require-link` | 要求两组系统之间必须有血流 |
| `no-cycle` | 严禁血流成环（**可选**：控制系统的血本来就会回流，所以默认不启用） |

**默认不启用禁环或单向分层规则**——这具身体的隐喻是解剖学，一上来强加"禁环"会把正常的反馈回路判成违规。新工程的 `init` 会自动装上"每个系统一条容量上限"的起步规则；已长起来的身体用 `action=freeze` 按现状固化（容量 = 现在 + 4，连接 = 现在已有的跨系统血流，按定义 0 违规）。

规则装没装、装了几条，看 `receipt.json` 的 `policy.rules`：`0` 就是"这一层还没开"。规则一旦装上就和结构错误同一条门禁——**写不进去，也出不了图**。
一个真实的例子（`fence-reverse-guard`）：12 条 = 禁"感知直连运动" + 5 条"这几组系统之间必须有血流" + 6 条"单系统器官数上限"（上限 = 当前数量 + 4，涨到上限就拦）。

### 3. 体检回执（receipt.json）

每次 `anatomy_render` 落一份回执，回答"你看的这张图，和当初通过体检的那份数据，是不是同一份"：

```json
{ "strict": true, "counts": {"organs":26,"flows":37}, "check": {"errors":0,"warnings":0},
  "policy": {"rules":0,"violations":[]},
  "anatomyHash": "b9b33da8…",           // 只跟数据有关：改一个字段就变
  "artifacts": {"anatomy.html": {"bytes":91120,"sha256":"a411d882…"}} }
```

### 4. 原子写与回滚

每个文件先写 `.tmp` 再改名；`scaffold` 批量写失败会**回滚到写入前状态**。

## 新工程：设计态先行（还没写代码就能共读）

新工程没有代码，锚点自然不存在——所以器官有 `status`：

| 状态 | 含义 | 体检要求 |
|---|---|---|
| `planned` | **设计态**：先把身体画出来 | 只要有名字和一句话；锚点、叙述、边界、成分都可以后补 |
| `active` | 已落地：代码写了 | 必须有锚点、叙述、边界、有效成分和契约（strict 下缺一件就拦） |
| `stale` | 代码变了，待复核 | 与 active 同要求 |

所以新工程第一天就能共读：`init` → `scaffold`（全用 `status: 'planned'`）→ `render` 出图，人和 AI 先对着这张图讨论"该长成什么样"；代码写完后逐个补锚点，再 `anatomy_activate` 落地。落地是有门槛的——缺锚点、叙述、边界、有效成分或契约都会被拒。通过体检代表结构与证据检查通过，仍需结合源码和测试复核实际职责。

## 人在界面上直接改（AI 读走，随时回退）

侧栏先展示共读摘要；切换机读后通过「工程对应与完整编辑」查看工程字段。人读模式仅显示自然语言和数学字段，机读模式显示完整工程字段；画布解剖层级不限制编辑能力。改动先落在本地副本上（图上立刻能看到效果），不会直接动文件。场景的触发、步骤说明、结果与验收条件同样可编辑并导出。

**器官**：名字 · 一句话 · 叙述 · 不负责什么 · 系统（可加减的多选）· 类型 · 状态 · 构成自 · 成分（名字+作用）· 可观测点 · 契约三段（收 / 发 / 必须始终成立）· 锚点（文件+符号+用途+依据）· 它进出的血脉（点一下跳到那条血脉）。
**血脉**：名字 · 一句话 · 起点 · 终点 · 物质 · 方向 · 走哪条管道 · 血里有什么 · 怎么观测 · 锚点。

- 列表末尾那一行就是"新增位"，而且**每一栏说的是自己的话**：`+ 加一条边界，例：不做坐标变换`、`+ 加一条锚点，例：gap_nav/detector.py`、`符号名，例：trace_corridor`——不再是一句通用的"新增一行"。
- **留空即删除，写进去即新增**；也可以点每行右侧的 `✕` 直接删（悬停才显形，不吵）。
- 有限取值的字段用**下拉**（类型 / 状态 / 构成自 / 起点 / 终点 / 物质 / 方向），不用去背取值拼写；系统是**多选 chip**（一个器官可以同属几个系统）。
- **底部改动条常驻**（不是"有改动才冒出来"）：`↶ 撤销` `↷ 重做` `保存到工程` `复制` `放弃` 一直在那儿，暂时用不上的按钮会置灰。状态文字会说清现在是"没有改动 / 改动 N 处未保存 / 已保存等 AI 落地"。
- 撤销 / 重做：`Ctrl+Z` / `Ctrl+Shift+Z`（或 `Ctrl+Y`）；每次进入一个字段记一个撤销点。刷新页面不丢（存在浏览器本地）。
- **删除器官要两步**：第一次点变成「再点一次确认删除」（6 秒后自动取消），确认后才删；删完改动条上立刻出现「↶ 撤销删除」，点一下就回来。
- 保存：改动条上「**保存到工程**」——浏览器支持时直接选路径存成 `anatomy-edits-<slug>.json`，否则退回下载并明确告诉你放进解剖体目录的 `edits/` 下；保存后状态栏变成"等 AI 落地后刷新本页看结果"。「复制」则把 JSON 直接粘给 AI。
- AI 侧：`anatomy_apply_edits` 读这个修改包落地。**人的修改照常过体检门禁**——改错了会被挡住，并把诊断退回给人（被挡时一个字节都不写）。
- 回退：每次写入前都留一版完整快照（`history.jsonl` + `history/rev-*.json`），`anatomy_history` 看账本、`anatomy_revert` 回到任意一版。回退本身也记一版，所以**退错了还能再退回来**。

### AI 怎么读到这些修改（不用人开口）

只要修改包落在**解剖体目录、`edits/`、工程根目录或下载目录**里，AI 一读工程就会看到：

- `anatomy_check` / `anatomy_history` 的结果里带 `pendingEdits`，并附一句提示；
- `show` / `brief` / `mapping` / `impact` / `digest` / `map` / `render` 默认全部拒绝返回旧快照或产物（`anatomy/pending-edits`）；`check` / `history` 仍能诊断。冲突复核可显式用 `anatomy_show({ inspectPending: true, level: "agent" })`，结果带 `snapshotOnly` 与待处理清单，不能当成合并后的意图；
- `anatomy_pending_edits` 按时间从旧到新处理各包；每包独立过版本与体检门禁。成功的包归档到 `edits/applied/`；失败的包留在原处，返回 `ok: false`、具体错误与失败数。不会静默用旧包覆盖新状态。自动发现只接受归属本工程的包，无归属旧包需手工指定文件导入。

一条完整的共读闭环：

```
人看图 → 发现某句叙述不对 → 界面上直接改 → 导出/复制修改包
      → AI 收到后 anatomy_apply_edits（过门禁）→ 落地并记一版
      → AI anatomy_show / digest 读到新版本 → 照它改代码
      → 谁改坏了 → anatomy_history 找到好的一版 → anatomy_revert
```


### 修改版本与源码复核

新图导出的修改包带 `body` 和 `baseHash`。只有当前 `anatomyHash` 与基线一致才会应用；直接传 `edits` 时，也要传编辑前从 `anatomy_show` 取得的 `baseHash`。出现 `anatomy/edit-conflict` 时，先用 `inspectPending` 检查当前快照并与修改包比较；把冲突包移出扫描目录留档，基于确认后的最新数据重新生成修改包。不能仅替换哈希来跳过复核。

没有基线的旧包默认拒绝；人工核对后，可通过 `anatomy_apply_edits({ file, allowUnversioned: true })` 单包导入。批量入口不允许跳过版本要求。包内有非法条目则整包不写，不会只应用其中合法的部分。

新写入的锚点自动记录文件 `sha256`，旧基线在普通写入中保留。代码变化后，即使名字不变也会出现 `anchor/source-changed`。复核代码、叙述、成分和契约后，对相关器官或血脉的写入显式传 `reviewSources: true`，才会更新已有基线；共享文件涉及多个对象时，使用 `scaffold` 一次复核并更新相关对象。该参数适用于 `scaffold` / `organ_put` / `flow_put` / `activate` / `apply_edits` / `pending_edits`。

这是文件级变化检查：注释或格式变化也会触发复核。符号检查是轻量文本检查，不是 AST 声明解析、工程覆盖率检查或业务正确性证明。`anatomy_check.sourceEvidence` 与 `receipt.json.sourceEvidence` 提供实际证据状态；旧图缺少指纹或根目录未确定时，摘要和图也会显示限制。

## 零容忍门禁（写与交付都拒绝带病通过）

体检分两档：**error 是硬门禁，warning 只记录**。

- **写入被拦**：`scaffold` / `organ_put` / `flow_put` / `remove`（含级联）在落盘前先跑一遍体检，只要有任何 error 就整条拒绝、**一个字节都不写**，并把诊断返回给你。
- **交付被拦**：`render` / `digest` / `map` 同样拒绝出产物——带着悬空引用或缺失的"一句话"的图与摘要，会误导读它的人和 AI。
- **架构规则同门禁**：`anatomy-policy.json` 里的违规和结构错误走同一条路，不因它是"约定"就放行。
- **锚点检查要"对的仓库根"**：锚点是仓库内相对路径，所以要 `repoRoot`。没给、且解剖体不在插件根目录下时，插件**不做锚点检查**并记一条 `anchor/not-checked`（warning）——它宁可说"这次没查"，也不用插件根去编一堆"文件不存在"的假错误：假错误会把人逼去 `force: true`，零容忍就废了。给了 `repoRoot` 就照旧真查（符号改名、写错路径一律拦）。
- **诊断绕过是 `force: true`**：仅绕过一般体检错误；不能绕过人读语言约束或要求验证的实现交付；它不能绕过修改包版本冲突、错误工程归属或待处理修改门禁。force 出的解剖图会在顶部打一条红色横幅，写明有几个 error、都是什么码，避免被当成正常产物。
- 删除也受保护：删器官时若有血脉连着、或有子器官以它为构成父级，默认拒绝；`cascade: true` 会一并删除血脉并解除子器官的构成关系。

诊断码与严格模式提升清单以 `lib/check.js` 为准。源码未检查（`anchor/not-checked`）或旧图未记录基线（`anchor/unreviewed`）会明确提示，不能解释为源码已验证。


## 新工程约定（四件事自己开，不用人提醒）

用户的要求：**建/改新工程时，下面四件事由插件与 AI 自动做掉。**

1. **解剖体住在它自己工程的目录里**：`anatomy_init({ repo: '<工程目录>', … })` → `<工程目录>/anatomy-<slug>/`；slug 取工程目录名。只报 `body: '<slug>'` 也能找到（会在 rootDir 下一层按约定找）。
2. **仓库根记进 `body.json`**：之后所有写入/交付自动拿它查锚点，不必每次传 `repoRoot`。回执里出现 `anchor/not-checked` 就说明根没定下来、这道保险没开。
3. **第四道门禁自动开**：`init` 装上"每个系统一条容量上限"的起步规则；血脉长齐后 `anatomy_policy({ action: 'freeze' })` 按现状固化连接与容量。`default` 回到起步规则，`clear` 清空。
4. **落地顺序**：两个已落地器官之间的血脉必须先有 `payload`，否则 `activate` 会拒（`anatomy/flows-need-payload`，直接点名是哪几条、并给出下一步）。

## 数据布局
